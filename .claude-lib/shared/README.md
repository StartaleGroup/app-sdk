## How it works

### Directory structure

```
your-project/
├── .claude-lib/
│   ├── shared/          # git subtree from this repo
│   │   ├── agents/
│   │   ├── commands/
│   │   ├── hooks/
│   │   ├── rules/
│   │   ├── skills/
│   │   ├── .scripts/
│   │   │   ├── install.sh  # first-time setup (gitignore + unpack)
│   │   │   ├── migrate.sh  # migrates existing .claude/ → .claude-lib/project/
│   │   │   ├── unpack.sh   # generates .claude/ from shared + project
│   │   │   ├── pack.sh     # reverses unpack: .claude/ → shared + project
│   │   │   └── push.sh     # pushes shared changes to source repo
│   │   └── README.md
│   ├── project/         # project-specific config (committed separately)
│   │   ├── agents/
│   │   ├── commands/
│   │   ├── rules/
│   │   └── skills/
│   └── shared-overridden/  # auto-generated, gitignored
├── .claude/                # auto-generated by install.sh, gitignored
└── src/
```

### The install/push cycle

**`install.sh`** merges `shared/` and `project/` into `.claude/`:
- Shared files get a `.shared` suffix (e.g., `react.md` → `react.shared.md`)
- Project files get a `.project` suffix (e.g., `api.md` → `api.project.md`)
- Skills get the suffix on the folder name (e.g., `prepr/` → `prepr.shared/`)
- When both shared and project have the same file, the shared version is moved to `shared-overridden/` so Claude Code only sees the project version

**`unpack.sh`** is the core of `install.sh` — generates `.claude/` from `shared/` + `project/`. Called by `install.sh` but can also be run standalone to regenerate `.claude/`.

**`pack.sh`** reverses `unpack.sh`:
- Reads `.claude/` and sorts files back into `shared/` and `project/` based on their suffix
- Restores overridden shared files from `shared-overridden/`

**`push.sh`** pushes shared changes to the source repo:
- Stages and commits any changes to `.claude-lib/shared`
- Pushes to the source repo on a timestamped feature branch

### The tier system

| Tier | Source | Suffix in `.claude/` | Scope |
|------|--------|---------------------|-------|
| shared | `.claude-lib/shared/` | `.shared` | All projects across the team |
| project | `.claude-lib/project/` | `.project` | Per-project config |
| local | engineer's machine | `.local` | Per-engineer, never committed |

Applied broadest to most specific: `shared → project → local`

## Day-to-day usage

### Pulling updates

```bash
git subtree pull --prefix=.claude-lib/shared claude-config master
bash .claude-lib/shared/.scripts/unpack.sh
```

### Pushing changes back

After editing files in `.claude/`, pack them back and push:

```bash
# If you edited files in .claude/, pack them back into shared/ and project/ first
bash .claude-lib/shared/.scripts/pack.sh

# Then push shared changes to the source repo
bash .claude-lib/shared/.scripts/push.sh
```

If you only edited files directly in `.claude-lib/shared/` or `.claude-lib/project/`, you can skip `pack.sh` and run `push.sh` directly.

PRs should target your project branch (e.g., `superapp`).

### Branch naming

Push branches are auto-generated as `from/superapp/sync-YYYYMMDD-HHMMSS`. For manual pushes:

```
from/<project>/<short-description>
```

### Team file promotion

When a PR containing shared config changes (files in `.claude-lib/shared/`) is merged to a project branch, a GitHub Action automatically opens a promotion PR to `master`. Once merged, `master` syncs back to all project branches.

## What's included

### Commands

| Command | Description |
|---------|-------------|
| `/claude-config-pull` | Pull latest shared config |
| `/claude-config-push` | Push shared changes to source repo |

Project-specific rules, agents, skills, and hooks should be added via `.claude-lib/project/` in each consumer repo.
